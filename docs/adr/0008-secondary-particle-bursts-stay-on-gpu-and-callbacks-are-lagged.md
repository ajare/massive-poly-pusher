# Secondary particle bursts stay on the GPU and callbacks are lagged

Particle events are authored on an emitter template and generated by the spawn
or simulation compute kernels. Spawn, death, first collision, and threshold-age
triggers write bounded GPU queues. A secondary particle burst consumes its event
on the GPU, allocates from the existing particle free list, applies the target
emitter template at the event position, and appends the new particles to the
current active list before compaction. It does not create a particle effect or a
CPU spawn command.

Spawn-triggered bursts may cascade through alternating GPU queues. Secondary-
burst target cycles are rejected, and a same-frame spawn chain is bounded to
eight event-processing stages.
Queue and particle-pool exhaustion drop work rather than overflowing storage or
requiring a count readback. Source and target emitter generations travel with
the event; destroying a target invalidates it immediately, so delayed GPU work
cannot be redirected into an unrelated emitter that reuses the same slot.

Decal, audio, light, and gameplay actions are typed notifications with an
authored integer payload. They remain in GPU storage unless the application
registers a callback for at least one external action. Registration lazily
activates a four-slot staging-buffer and fence ring. Completed slots are polled
with a zero timeout after a minimum two-frame lag; the renderer never waits for
the frame that generated an event. Ring pressure skips a readback sample rather
than stalling simulation. Clearing the last callback removes the readback path.

The alternatives were to turn every event into a CPU spawn command, which would
violate the GPU ownership of particles and require per-frame synchronization,
or to make event processing part of a render graph pass, which would repeat it
for reflections and other views in conflict with ADR 0005. Event generation and
consumption therefore run once beside simulation before pure draw passes.

A secondary particle burst targets another emitter template in the same live
particle effect. This is not child-effect composition: child particle effect
asset references, shared transforms, and group lifetime semantics remain the
scope of #38. Likewise a light notification does not inject thousands of dynamic
or volumetric lights; actual particle lighting injection remains #37.
